# 成本公式管理设计（C3/C4）

> 状态：**待评审**（尚未动代码）
> 目标：把「各品类成本公式 + 公式中各部分占比」从硬编码变为**可私密管理、可版本化、可回归验证的资产**，
> 同时守住核心思想——**公式是稳定内核，价格是易变外部数据，引擎确定性计算，输出带置信度**。
> 前置：A1 黄金基线回归已建立（`npm run test:golden`），本方案所有改动都必须能被它观测到。

---

## 0. 结论先行（含一处自我修正）

- **要单开页面**，但页面形态不是「写公式的文本框」，而是**按维度组织的「成本项配方表」**。
- **表达形式改为「结构化配方优先 + DSL 兜底」**。这是本次调研后对先前建议的**修正**——
  先前我建议「DSL 表达式为主」，调研成熟产品后发现**反例证据充分**，理由见 §2。
- **私密性靠「部署开关 + fail-closed 鉴权」，不靠「藏个 URL」**。公网实例默认不含公式管理页。

## 1. 市场调研：同类产品怎么管

| 产品 / 领域 | 怎么管计价逻辑 | 关键启示 |
|---|---|---|
| **GelatoConnect Estimator**（印刷估价，最接近本域） | 不提供"写公式"。在 `Estimate Setup → Print Machines` 配置**机台档案**：click rate、油墨覆盖率档位（Very Light/Standard/Heavy）、工时费率、运行速度、起步时间。报价由这些**结构化字段**算出 | 行业主流是**配置参数**，不是编写公式 |
| **贯通印刷报价软件**（国内） | "系统本身没有任何固定的参数，所有的计价参数都是由用户设置的…数字逻辑函数矩阵构成的自动计算系统"；另有「分项成本利润 / 总成本加利润」两种**模式开关** | 参数矩阵驱动 + 模式开关，公式内建不暴露 |
| **Salesforce CPQ** | Price Rules + Lookup Object（把矩阵外置成表）；一等机制优先（Discount Schedule / Block Pricing / Percent of Total），规则只在必要时用 | **一等机制优先**，规则是最后手段 |
| **CPQ 架构实践共识** | "Adopt a small library of reusable functions rather than many bespoke formulas…makes pricing auditable and unit-testable"；生命周期 Draft → QA → Production；配置要进源码管理 | 少量可复用函数 > 大量定制公式 |

**三条被反复警告的坑（我们应正面规避）**

1. **规则森林**：50+ 条规则 → 慢、难维护、易冲突。对策：矩阵外置成表、一等机制优先。
2. **硬编码可变值**："材料成本每月变但硬编码在规则里 → 很快不准。可变数据从外部系统取。"
   → 正对应我们 **KB 优先** 的设计，公式里只引用 KB key，不写死数值。
3. **隐形逻辑**："如果规则复杂到销售自己都看不懂价格怎么算的，信任就崩了。要文档化、要给出拆解。"
   → 正对应我们五维拆解 + 每维 breakdown 的做法。

## 2. 为什么改为「结构化配方优先」（对先前建议的修正）

我先前建议 DSL 表达式为主。调研后改主意，理由：

| 维度 | DSL 自由公式 | 结构化配方 |
|---|---|---|
| 可审计 | 公式变成字符串，审计要读表达式 | 每行是「成本项 + 计算方式 + 参数 + 条件」，一眼看懂 |
| 可单元测试 | 表达式整串测，难定位 | 每种「计算方式」是独立纯函数，可单测 |
| 回归可观测 | 改一个字符影响难估 | 改哪一行、影响哪些用例，试算面板直接显示 |
| 上手成本 | 需要学表达式语法 | 下拉选 + 填参数 |
| 表达力 | 强 | 弱于 DSL（故保留 DSL 兜底 ~5% 场景） |

**结论**：一等机制覆盖 95% 成本项，DSL 只作兜底。这也符合「公式是稳定内核」——
稳定内核应该被**结构化**地表达，而不是变成一堆自由文本。

## 3. 形式：页面怎么放、怎么私密

### 3.1 放哪

**单开页面 `/admin/formula`，不进任何导航**（与现有 `/admin/knowledge` 一致的做法），需显式 URL 访问。

### 3.2 私密性（重点：公网部署后公式是护城河）

现有 `/api/admin/knowledge-base` 的 `checkAuth` 是 **fail-open**：
> `if (!token) return true; // 未配置则开放`

这对知识库尚可接受，但**对公式页面是致命的**——公网部署若忘记配 token，公式可被任意读写。

**公式管理必须 fail-closed**：

| 环境 | FORMULA_ADMIN_TOKEN | 行为 |
|---|---|---|
| 你本机 | 在 `.env.local` 配置 | 页面可访问、可改 |
| 公网获客实例 | **不配置** | 页面与 API 均 **404/401**，公式不可见不可改；引擎用内置默认配方 |

补充：`/admin/formula` 路由在公网构建时可通过 env 直接**不注册**（更彻底，连页面都不打包）。

### 3.3 安全求值（DSL 兜底部分）

- 服务端沙箱求值，候选 `expr-eval` 或 `json-logic`
- **白名单函数/运算符**，超时保护
- **绝对禁用 `eval` / `new Function`**（项目要上公网，等于开后门）

## 4. 数据模型

### 4.1 三层结构

```
ProductType（品类，已有 config/products/*.ts）
  └── Dimension（维度：material / labor / process / design_plate / finance_other，已有）
        └── CostItem（成本项 · 新增，本方案核心）
```

### 4.2 CostItem（配方行）

| 字段 | 说明 |
|---|---|
| `id` / `productType` / `dimension` | 归属 |
| `name` | 成本项名（面纸 / 坑纸 / 油墨 CMYK / 制版费 / 管理费…） |
| `kind` | **计算方式**（一等机制枚举，见 4.3） |
| `params` | JSON：该 kind 所需参数，**数值一律用 `{ kb: "category:key", fallback: n }` 引用 KB，不写死** |
| `conditions` | JSON：适用条件（如 `fluteType != "none"`、`surface in [foil,emboss]`） |
| `weight` / `enabled` | 权重与启停（**「各部分占比」即落在这里**） |
| `sortOrder` | 展示与计算顺序（percent_of 需要依赖顺序） |
| `version` / `effectiveFrom` / `effectiveTo` | 版本与时间维度（复用 C6 设计） |
| `status` | `draft` / `active` / `archived` |
| `note` | 该系数的经验依据（护城河的可读化沉淀） |

### 4.3 kind 一等机制清单（先覆盖现有硬编码，逐步扩）

| kind | 含义 | 覆盖的现有公式 |
|---|---|---|
| `flat` | 固定金额 | 设计费 800、打样费 300 |
| `unit_rate` | 单价 × 件数 | 模切、粘盒（按件） |
| `area_rate` | 单价 × 面积 | 覆膜/UV/烫金（元/m²） |
| `weight_rate` | 重量 × 吨价 ÷ 1000 | 面纸、坑纸、灰板 |
| `ink_rate` | 面积 × 墨量(g/m²) × 单价(元/kg) ÷ 1000 | 油墨 CMYK / 专色 |
| `tiered` | 阶梯（按数量分档） | 数量折扣、克重阶梯 |
| `stepped` | 起步价 + 超出部分 | 印刷起步价 |
| `percent_of` | 按某基数取百分比 | 物流 3%、管理费 6%、利润 8% |
| `formula` | **DSL 兜底**（白名单沙箱） | 长尾 / 特殊客户口径 |

> 每种 kind 实现为**独立纯函数**，单测覆盖；引擎侧 ` specialists.ts` 改为「读配方 → 逐项求值 → 汇总」，
> **读不到配方时回退现有硬编码**（复用 KB 那套成熟套路，保证不破坏现有行为）。

## 5. 页面交互（原型已附）

1. **顶部**：品类选择、版本选择（生效中 / 已归档）、试算、保存草稿
2. **主体**：按维度分组的配方表，每行 = 成本项 / 计算方式（下拉）/ 参数（可指向 KB）/ 适用条件 / 启用
3. **试算面板（保存前必跑）**：输入一组参数 → 输出各维度结果 + **与黄金基线的偏差** + **9 个黄金用例通过数**
   - 这一步把 A1 的回归保护**前移到你改公式的当下**，而不是等提交才发现

## 7. 决策记录（2026-08-29 用户拍板）

| # | 议题 | 决策 |
|---|---|---|
| 1 | 占比怎么表达 | **直接可改的百分比/权重**（如管理费 6%、利润 8%），而非由金额反推显示。另：AI 可给**行业参考建议**（如"同类彩盒管理费常见 5~8%"），但只是建议、不自动写入 |
| 2 | 版本审批 | **免审批**，改完直接生效；但**审计日志必须有**（谁/何时/改了哪个成本项/前后值），且保存前跑试算 |
| 3 | DSL 兜底是否现在做 | **现在做，但做最小安全版**（见 7.1） |
| 4 | 权限体系 | **后续接入用户注册登录后再按角色控制公式管理权限**。过渡期方案见 7.2 |

### 7.1 DSL 兜底：为什么现在做、怎么做

**结论：现在做**——后补的代价更高（要再动一次表结构、再改一次页面、再回归一遍），
而它是与其他 kind 平级的独立模块，现在做不阻塞 F2~F5。

但必须是**最小安全版**：

- 白名单运算符：`+ - * / %`、括号、比较、三元
- 白名单函数：`min max round ceil floor abs clamp`（后续按需加，加一个审一个）
- 变量只能引用**上下文白名单字段**（如 `weight / area / quantity / pricePerTon`），不暴露任何全局对象
- 服务端沙箱求值，带超时（50ms）与结果校验（必须是有限 Number）
- **绝对禁用 `eval` / `new Function`**
- **默认关闭**：`kind = "formula"` 仅在显式选用时启用；系统开关 `FORMULA_DSL_ENABLED` 未开启时，
  即使配了 formula 项也回退并告警

### 7.2 ⚠️ 时间差风险（第 4 条决策的隐患）

用户注册登录属**三期之后**，公网部署属**一期**。中间会存在一个
**"公网已上线、但还没有用户系统"的窗口期**——这段时间没有"按角色控制权限"可用。

**过渡期靠这两条兜底（互为备份，缺一不可）**：

1. **fail-closed 鉴权**：未配置 `FORMULA_ADMIN_TOKEN` 时一律拒绝（与现有 KB 页面的 fail-open 相反）
2. **公网构建不注册路由**：`/admin/formula` 在公网构建时通过 env 不打包，页面根本不存在

否则窗口期里，公式（护城河）可被任意读写。
